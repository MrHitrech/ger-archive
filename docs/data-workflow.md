# Подготовка и проверка данных

## Что считается подтверждением

`verified` — игровой факт проверен человеком по доступному оригиналу, разрешённому экспорту или самой игре. Требуются `reviewed_by`, `reviewed_at`, свидетельства и отсутствие пропусков. `partial` — часть фактов имеет источник, но остаются пробелы или доступна только поисковая копия. `unverified` — сведения ещё не сверены.

Источники в `data/sources.json` указывают способ получения: `search_index`, `manual_original`, `manual_game`, `permitted_export`. Валидация запрещает объявлять игровую запись `verified`, если её доказательства основаны только на поисковом индексе. У всех начальных записей статус `partial`; нет выдуманной проверки по игре.

Для каждого свидетельства `data/evidence/claims.json` хранятся ID источника, явно выбранный раздел, точный фрагмент, имя копии и SHA-256. Копии лежат в `data/evidence/`. Проверяется и хеш файла, и наличие фрагмента. Это проверка происхождения, а не истинности сведений Wiki. Снимки поиска не являются оригинальным HTML и не предоставляют номер ревизии.

## Сначала источник, затем запись

1. Проверьте, что источник разрешает использование и автоматический доступ. Сохраните ссылку, авторов/историю, лицензию и способ получения. Не обходите HTTP 403, robots или другие ограничения.
2. Выделите раздел **God Eater Resurrection**. На смешанной странице внешний заголовок об игре обязателен. Не переносите значения из соседнего Burst, GE2/GE2RB или GE3.
3. Сохраните разрешённую копию с устойчивым именем. Для копий поиска оставьте `acquisition: search_index` и статус `partial`.
4. Добавьте свидетельства с точными фрагментами, разделом и SHA-256. У разных рецептов/условий должны быть отдельные свидетельства.
5. Подготовьте нормализованный JSON. Сопоставьте материалы и предметы по ID и точным оригинальным названиям; сходные русские переводы не объединяют записи.
6. Проверьте конфликтующие значения по другому надёжному источнику или игре. Не выбирайте значение по внешнему сходству.
7. Запустите предварительный импорт, затем примените его и выполните проверки.

## Повторяемый начальный импорт

Для установленной игры используется отдельный процесс [импорта игровых файлов](game-data-import.md): `game:extract` и `game:import`. Он дополняет базу, сохраняет ID и происхождение из бинарных таблиц. Команда ниже воспроизводит только исторический набор Wiki; после игрового импорта она может показать конфликты и не должна использоваться для восстановления новой базы.

```sh
npm run data:import -- --dry-run
npm run data:import
```

Импортёр читает только сохранённые локальные копии; во время команды сетевых запросов нет. В `scripts/import-seed.mjs` заданы явные границы и ожидаемое число полных строк каждого импортируемого семейства. Если копия изменится, нарушится структура или пропадут строки, импорт должен завершиться ошибкой. Другие группы не достраиваются автоматически.

`node scripts/import-data.mjs --rebuild-seed` восстанавливает исходные игровые записи из копий **вместо текущего набора** и сохраняет сопоставимые переводы. Это инструмент разработчика для чистого исходного набора, не обычная команда обновления: вручную добавленные факты могут быть удалены. Перед её использованием сохраните свою работу в Git.

## Ручное добавление / разрешённый экспорт

Подготовьте JSON-объект с любыми из массивов `materials`, `items`, `recipes`, `missions`, `aragami`, `locations`, `drops`, `sources`, `evidence`, `translations`. Записи должны соответствовать `data/schema.json`. Остальные массивы существующей базы сохраняются.

```sh
npm run data:import -- --input path/to/reviewed-batch.json --dry-run
npm run data:import -- --input path/to/reviewed-batch.json
npm run translations:prepare
npm run data:report
npm test
npm run build
```

Сначала проверяется весь объединённый набор, включая связи и копии; затем JSON-файлы заменяются по одному с атомарной записью каждого файла. Команда не является транзакцией файловой системы: при прерывании проверьте изменения в Git и повторите валидацию.

Существующий ID с другими полями создаёт `data/reports/import-conflicts.json`; команда завершается с ошибкой до записи игровых файлов. В отчёте находятся старое и новое значения. Разберите разницу, подтвердите её и явно отредактируйте исходные JSON или подготовьте новый подтверждённый вариант. Скрытого перезаписывания и автоматического разрешения конфликтов нет.

`--dry-run` не записывает игровые файлы, но при конфликте оставляет отчёт для разбора. Отчёты об ошибках импорта являются рабочими артефактами, не игровыми данными.

## Идентификаторы и связи

Все игровые сущности имеют ID вида `ger-<тип>-<12 hex>`. Начальный импорт получает стабильные ID функцией `idFor` из точного ключа источника с версией игры. Перевод не участвует в ключе. После присвоения ID он остаётся идентичностью записи; переименование делается явно с сохранением связей. `+`, `II`, `EX` и различия вариантов не отбрасываются.

Типы ID: `m` — материал, `i` — снаряжение, `r` — рецепт, `q` — миссия, `a` — арагами, `l` — локация, `d` — способ получения. Ключ миссии содержит тип, сложность, локацию и название. Дополнительные варианты обозначаются отдельно. При появлении нескольких вариантов с одинаковыми этими полями задайте отдельный исходный ключ варианта; не объединяйте их.

В основной базе нет дублирующихся списков `used_in` или `sources`: обратные связи выводятся по ID из рецептов и способов получения. Так изменение рецепта не оставляет устаревшие ссылки в материале.

## Вероятности и контекст добычи

- `drop_rate` — число 0–100 или `null`. `null` никогда не означает 0%.
- `quantity` — положительное целое или `null`, когда количество не установлено.
- Способ получения отделён от миссии, противника, локации и условия. Награда миссии не считается добычей с каждого находящегося в ней арагами.
- Пожирание, разрушение части и дополнительные награды — разные записи. Для разрушения требуется отдельное условие с конкретной частью.
- Повторяющиеся строки не суммируются без доказанной независимости слотов. Если её нельзя установить, `slot`, вероятность и количество остаются неизвестными; проблема фиксируется в карантине.
- Таблица наград может иметь суммы больше 100%, если строки относятся к разным наградам/слотам. Валидация не требует суммы 100% и не вычисляет общий шанс из несопоставимых строк.
- Ранг материала показывает только известное получение. Ранг рецепта нельзя автоматически объявить рангом доступности ингредиента.
- Время лимита миссии не считается временем её прохождения. Сортировка по проценту не является рекомендацией самого быстрого фарма.

В текущем наборе Pixie Thorn связан с **Mayflies**, а не с Corrupt Cocoon: заголовок контекста важнее совпадения поисковых слов. Две автоматические строки Impure Grease с шансами 100% и 33% не превратились в 133% или гарантированную награду. Проценты пожирания Ogretail из секции Burst исключены. DEF с ингредиентом `1x Ogretail`, дублирующийся Item Effect и MatPlaceholder1 не импортированы.

## Создание, улучшение и несколько целей

У рецепта есть `operation: craft | upgrade`, целевой `item_id`, `from_item_id` для улучшения, ингредиенты с положительными количествами, стоимость `cost_fc` или `null` и ранг. Альтернативные рецепты одного предмета имеют разные ID. Предшественник не становится обычным расходуемым материалом.

Дерево и калькулятор используют эти связи. По умолчанию каждая цель — отдельный физический экземпляр. Общая цепочка включается только явно; одно и то же промежуточное улучшение тогда учитывается один раз. Два несовместимых конечных ответвления для одного экземпляра дают ошибку. Запас материала вычитается один раз после суммирования, а не независимо у каждой цели.

## Русификация

`data/translations/en.json` сохраняет оригиналы. `ru.json` содержит ID, английское и русское название, альтернативные названия, источник и один из статусов `official`, `verified`, `unverified`.

```sh
npm run translations:prepare
```

Скрипт сопоставляет существующий словарь по ID, сохраняет редакционные решения и готовит очередь `data/reports/translation-review.json`. `drafts.json` — только предложения проекта. Они получают `unverified`; скрипт не подключается к сервису машинного перевода и не выдаёт предложения за официальные названия. Подтверждённые русские соответствия из доступного источника можно добавить пакетным импортом вместе со свидетельствами и проверяющим.

После ручного изменения переводов выполните `translations:prepare`, `data:report`, тесты и сборку. Английское имя в словаре должно точно соответствовать исходной записи. Неподтверждённое одинаковое русское имя не служит основанием для объединения ID.

## Отчёт и границы готовности

`npm run data:report` обновляет `quality-report.json`. `data:check` и сборка отклоняют устаревший отчёт. Для каждого раздела указаны импортированные, проверенные, частичные, непроверенные и содержащие пробелы записи. Очередь `missing` перечисляет пропуски каждой записи; карантин перечисляет вопросы импорта.

`universe_total` и `missing_from_universe` остаются `null`, пока нет надёжного полного перечня контента, сверенного с ID. Для миссий сборки 1412844 такой перечень установлен: 515 нативных строк сведены к 363 заданиям и 21 дополнительному этапу. В отчёте миссий `total`/`universe_total` равны 363, `missing_from_universe` — 0; `records_total` (384) включает дочерние этапы. Остальные разделы не получают заявлений о полноте из количества найденных страниц или текущих рецептов. Перед полноценным релизом требуется отдельно завершить работу с источниками, лицензионными уведомлениями, условиями открытия, таблицами наград, разновидностями арагами, исходными названиями и переводами.
